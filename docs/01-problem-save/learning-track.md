# 학습 트랙 — 문제 저장 템플릿

출처: Feynman Technique (Richard Feynman) — 어떤 개념을 안다고 착각하는 것과
실제로 아는 것의 차이는 "전문 용어 없이 남에게 설명할 수 있는가"로 드러난다는
학습법. 네 단계(개념 선택 → 쉬운 말로 설명 → 막히는 지점 식별 → 단순화/비유)
중 이 템플릿은 2~3단계를 필드로 강제한다.

## 템플릿

```
주제:
왜 배우는가(동기):
학습 자료(출처):
핵심 개념 요약(Feynman 기법 — 전문 용어 없이 내 언어로 설명):
막힌 부분/질문(있다면):
완료 기준(무엇을 할 수 있으면 끝났다고 볼 것인가):
상태(학습중 / 이해완료 / 적용해봄):
```

## 핵심 규칙

"핵심 개념 요약"에 원문 용어를 그대로 베끼면 안 된다 — Feynman 기법의 핵심은
**설명하다가 막히는 지점**이 바로 실제로 이해 못 한 부분이라는 것이다. 막히면
솔직하게 "막힌 부분/질문"에 적고, 원자료로 돌아가 확인한 뒤 다시 쉬운 말로
써본다.

## 작성 예시

```
주제: Conventional Commits
왜 배우는가: 이 저장소의 커밋 메시지 형식이 지금까지 느슨하게 관행적으로만
  맞춰져 있어서, 나중에 커밋 이력만 보고 변경 종류(기능/버그수정/문서)를
  자동으로 구분하기 어렵다.
학습 자료: https://www.conventionalcommits.org/en/v1.0.0/
핵심 개념 요약: 커밋 메시지 첫 줄을 "타입(범위): 요약" 형태로 고정한다
  (feat/fix/docs/refactor/test/chore 등). 사람이 아니라 기계가 커밋 이력만
  읽어도 "이건 기능 추가, 이건 버그 수정"을 구분할 수 있게 하는 게 목적이고,
  여기서 더 나아가면 feat=minor, fix=patch, "BREAKING CHANGE"=major로 버전을
  자동 계산하는 데까지 쓰인다(SemVer와 연결).
막힌 부분/질문: 이 저장소가 지금까지 써온 "feat: ...", "docs: ..." 형식이
  이미 이 규격과 거의 같다는 걸 확인 — 완전히 새로 배운 개념이라기보다는
  이미 하던 관행에 이름과 근거가 붙은 경우였다.
완료 기준: 커밋 메시지 첫 줄만 보고 그게 기능/버그수정/문서 중 뭔지 맞힐 수
  있으면 끝.
상태: 이해완료
```
