# ADR-0001: 워크플로우 인터페이스를 파일+Claude Code 스킬 하이브리드로 결정

- Status: Accepted
- Date: 2026-09-17

## Context

2단계에서 확정된 요구사항([applied-example.md](../../02-problem-analysis/applied-example.md)):

- FR1 (Must/Basic): 새 문제/프로젝트 시작 시 트랙별 저장 템플릿을 **제공**해야 한다
- FR3 (Must/Performance): 회고 완료 시 카탈로그/체크리스트에 **1회 명령으로** 추가할 수
  있는 진입점을 제공해야 한다
- Supportability(NFR): 새 트랙 추가 시 기존 파일 무변경으로 확장 가능해야 한다

지금까지는 `docs/` 아래 순수 마크다운 파일로만 구조를 만들었는데, FR1의 "제공"과 FR3의
"1회 명령"은 사람이 파일을 직접 찾아서 복사하는 수준을 넘어서 **행동을 유도하는 인터페이스**를
요구합니다.

## Decision

**파일 구조(데이터 계층) + Claude Code 커스텀 스킬(인터페이스 계층)의 하이브리드**로 간다.

- `docs/` 아래 템플릿·카탈로그·체크리스트는 그대로 "진실의 원천(source of truth)"으로 유지
- 이후 4단계(패턴 구현)에서 `.claude/skills/dev-workflow/SKILL.md` 스켈레톤을 만들어,
  Claude Code 세션에서 트리거되면 해당 트랙 템플릿을 불러와 채우게 하고, 회고 완료 시
  `catalog/patterns.md` / `catalog/checklist.md`에 항목을 추가하는 절차를 수행하게 한다
- 스킬은 파일 구조를 대체하지 않고 "파일을 다루는 절차를 아는 안내자" 역할만 한다

## Considered Alternatives

1. **순수 파일 구조만 유지** — 기각. FR3의 "1회 명령"을 만족 못 함(사람이 매번 수동으로
   두 파일을 열어 편집해야 함). Supportability는 만족하지만 Must 요구사항 미달.
2. **독립 실행형 CLI 스크립트(Python/Node 등) 제작** — 기각(지금은, Won't). 개인 도구
   치고 과잉 엔지니어링. 유지보수 부담(런타임/의존성 관리)이 원문제 해결 가치보다 큼.
   나중에 스킬만으로 부족하면 재검토.
3. **파일+Claude Code 스킬 하이브리드 (채택)** — 이미 사용 중인 도구(Claude Code) 위에서
   동작하므로 추가 설치·의존성이 없고, FR1·FR3를 실제 명령으로 만족시킴.

## Consequences

**장점**
- FR1, FR3가 "문서"가 아니라 실제로 실행 가능한 절차가 됨
- 기존에 만든 `docs/` 구조를 버리지 않고 그대로 재사용 (마이그레이션 비용 없음)
- Supportability 유지: 새 트랙 추가 시 스킬 로직을 바꾸지 않고 새 템플릿 파일만 추가 —
  단, 스킬이 트랙 목록을 하드코딩하지 않고 폴더를 순회하도록 4단계에서 설계해야 함
  (아래 리스크 참고)

**단점 / 리스크**
- Claude Code 환경에 종속됨 — 다른 에디터/환경에서는 `docs/`만 수동으로 봐야 함
  (개인 도구이므로 감수 가능한 트레이드오프로 판단)
- 스킬 로직이 트랙을 하드코딩하면 Supportability NFR을 어길 수 있음 → 4단계 구현 시
  "새 트랙 폴더만 추가하면 스킬이 자동 인식"하도록 설계할 것을 제약조건으로 명시
- 스킬의 동작을 자동화된 테스트로 검증하기 어려움 → Planguage Usability 목표(5분 이내
  작성)는 수동으로 타이머를 재서 확인하는 방식으로 대체
